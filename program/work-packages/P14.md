# P14 — Independent integration and profile release qualification

Status: implementation and qualification pending. Dependencies and coverage are canonical in [plan.json](../plan.json); mutable state is in [state.json](../state.json).

## User-visible outcome

An independent verifier can install and reproduce the declared product profile, and users receive a precise capability, environment and limitation statement.

## Implementation work

1. Select the release profile and resolve its conditional prerequisite set from PROGRAM.md. The graph dependency on P05 enables local-runtime qualification only; richer profiles additionally require their M2–M6 package gates.

2. Reproduce critical experiences and invariants on the exact submitted revision and tuple. Include installation/update/recovery, privacy, export, accessible interaction and real provider boundaries relevant to the profile.

3. Compare user-task and resource measurements with the baseline. Verify that demos, evidence, status and documentation refer to the same behavior and version.

4. Prepare release notes, reproducible commands, known exclusions, rollback/recovery instructions and license/distribution evidence. Public publication requires actual owner authorization.

## Acceptance

**P14-A1.** The profile enumerates qualified packages, experiences, invariants, environment tuple and provider/model versions; no omitted optional capability is implied.

**P14-A2.** A different verifier reproduces both positive and negative behavior on a clean environment; missing, stale or mocked evidence cannot qualify a runtime claim.

**P14-A3.** All profile-critical failures are resolved or the profile remains blocked. Optional unavailable features are explicitly absent, not “passed with caveats.”

**P14-A4.** Upgrade/backup checks for a runtime-only release cover runtime/data lifecycle without claiming P11 image qualification.

**P14-A5.** Changed code/contracts after verification trigger an impact assessment and affected reruns before the final evidence is accepted.

## Failure and recovery coverage

Fresh install failure, stale evidence revision, hidden external dependency, incomplete profile prerequisites, regression, missing license clearance and an unreproducible verifier recipe.

## Scope boundary

Declaring the entire roadmap done because one profile passed. P14 can produce several versioned profile qualifications; state/evidence must keep their scopes distinct.

## Handoff and evidence

Qualification kind: `engineering`. Independent review can qualify this procedure/tooling scope without implying that a runtime profile has passed. Each profile still requires separate real runtime evidence and qualified prerequisites.

Record the exact submitted revision, target tuple, commands, exit codes, artifact/receipt digests, observed negative outcomes and reproduction recipe. Link applicable experiences (E01, E02, E03, E04, E05, E06, E07, E08, E09, E10) and invariants (I01, I02, I03, I04, I05, I06, I07, I08, I09, I10, I11, I12, I13, I14, I15, I16, I17, I18, I19, I20). Use [qualification policy](../../conformance/ACCEPTANCE.md) and [execution procedure](../EXECUTION.md). A separate verifier reproduces the package-critical claims; absence of a verifier leaves work implemented, not qualified.

P14 is the qualification activity/tooling package, not a global release switch. Keep its work implemented when the process is ready; record each release outcome under `state.json.profiles[profile_id]` with profile-scoped evidence. Marking one profile qualified never qualifies another profile or all optional packages.
