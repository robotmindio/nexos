# P00 — Scoped inventory and qualification tuple

Status: implementation and qualification pending. Dependencies and coverage are canonical in [plan.json](../plan.json); mutable state is in [state.json](../state.json).

## User-visible outcome

A new agent can reproduce the chosen development environment and implement the first real capability without guessing integration ownership or hardware assumptions.

## Implementation work

1. Inspect the existing integration evidence and the smallest relevant code at a pinned revision. Recheck agent-session-relay, workspace-provisioner, PC control authority and Bifrost surfaces before inventing equivalent infrastructure. Distinguish an observed API from a qualified NexOS integration.

2. Record the exact x86_64 CPU-only QEMU/KVM NixOS guest, host kernel, Nix/Nixpkgs revision, Rust toolchain, SQLite version and required privileges. Commit actual lock/pin data after resolving it; unknown versions remain explicitly unresolved.

3. Choose one first operation: create or transform an artifact inside a managed workspace with a deterministic command. Define its input/output, effect, grant, budget and receipt contracts and the host boundaries it needs.

4. Establish canonical state ownership, module boundaries and a narrow helper interface. Freeze only contracts needed by P01–P02. Give optional integrations their own audit work rather than making all product work depend on a complete monorepo review.

## Acceptance

**P00-A1.** A clean environment can reproduce the pinned development setup and run the repository specification checks; report separately whether VM boot and privileged containment are available.

**P00-A2.** An inventory maps each inspected candidate to exact repository/path/revision, observed operation, gap, owner and reuse/extend/defer decision.

**P00-A3.** Valid and invalid examples cover the first capability contract. An incompatible protocol version and unknown privileged effect fail validation.

**P00-A4.** The recorded qualification tuple names required enforcement facilities and explicit exclusions; no actual hardware or integration pass is inferred from documentation.

## Failure and recovery coverage

Unavailable monorepo access blocks the affected integration audit. Missing KVM/privileges blocks the stated runtime tuple; keep specification work moving and prepare a runner recipe. Do not silently downgrade the threat model.

## Scope boundary

No full desktop, generic scheduler, complete ontology implementation, blanket monorepo audit or invented release hashes.

## Handoff and evidence

Qualification kind: `specification`. An independent reviewer must verify the scoped inventory, contracts and reproducible environment acceptance. A bare validator pass is insufficient. Keep `qualifies_runtime: false` for this non-runtime claim; qualification of P00 does not claim that NexOS runs.

Record the exact submitted revision, target tuple, commands, exit codes, artifact/receipt digests, observed negative outcomes and reproduction recipe. Link applicable experiences (E08) and invariants (I16, I18, I20). Use [qualification policy](../../conformance/ACCEPTANCE.md) and [execution procedure](../EXECUTION.md). A separate verifier reproduces the package-critical claims; absence of a verifier leaves work implemented, not qualified.
