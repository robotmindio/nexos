# ADR 0001: Linux runtime and NixOS reference environment

Status: accepted design direction; implementation and platform qualification pending.

## Context

NexOS needs a working environment in which humans and agents share typed capabilities, authority and recoverable work. It also needs drivers, conventional applications, isolation mechanisms and a repeatable way to qualify behavior. Building an operating-system distribution before proving that experience would devote early effort to installation and compatibility rather than product value.

## Decision

Build a portable Linux runtime first. Use upstream Linux, an established desktop/compositor, a modular `nexosd` control service and small substrate adapters. Use NixOS for the first pinned VM qualification environment and later as a reference distribution. The initial target is CPU-only, local and limited to managed workspace state. Exact release/build pins and image digests are implementation evidence to establish in P00, never placeholders to invent in a design document.

NixOS is a provider of declarative system configuration and realized generations. Application checkpoints, snapshots, effect reconciliation and backup remain separate contracts. Do not make Nix, a cloud workflow engine or a semantic database a prerequisite for every deterministic runtime operation.

## Consequences

The team benefits from existing Linux hardware and tooling and can validate a coherent product before maintaining a distribution. It accepts Linux's shared-kernel threat model for the separately qualified OS sandbox profile. Higher-risk VM isolation, accelerators, other architectures and federation require their own qualification.

Portability requires explicit capability discovery and adapter semantics; a weaker host cannot silently claim a stronger profile. NixOS offers a useful reference build environment while introducing packaging expertise and compatibility work. Runtime contracts preserve the option to ship first on another Linux distribution if product evidence favors that route.

## Alternatives and revisit criteria

A kernel fork or new microkernel is deferred because the proposal has not demonstrated a requirement that existing Linux facilities cannot satisfy. Genode, seL4, Qubes and Plan 9 may inform capabilities, compartmentalization and distributed design; they are not hidden dependencies. A custom compositor or filesystem likewise requires a measured unmet product need.

Revisit this decision when a reproducible qualification failure or adoption blocker identifies the missing property, compares smaller alternatives, and names a maintenance owner. The [platform matrix](../PLATFORM.md), [architecture](../ARCHITECTURE.md) and [state contract](../STATE-AND-RECOVERY.md) are the controlling implementation references.
